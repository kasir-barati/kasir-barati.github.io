Kubernetes / Deployments

Recreate and RollingUpdate are the two deployment strategies built directly into a Kubernetes Deployment. But they are not the only deployment patterns you can use with Kubernetes. Blue-green and canary deployments are also common, but keep in mind each of of these strategies solve different problems.

The mental model

There are two different questions

Kubernetes gives you primitives for replacing Pods. A deployment strategy describes the broader way you introduce a new application version and move traffic to it.

Strategy 01 Kubernetes built-in

Recreate

Kubernetes terminates the existing Pods before creating Pods for the new version. It is simple, but it creates a window where no application Pods are available.

Good when

Downtime is acceptable and simplicity matters more than availability.

Main drawback

Strategy 02 Kubernetes built-in

Rolling update

Kubernetes incrementally replaces old Pods with new Pods. During the rollout, both versions can exist at the same time, allowing the application to remain available.

Strategy 03 Deployment pattern

Blue-green deployment

Run the old and new versions as separate environments. Test the new environment, then switch the traffic-routing layer from blue to green. The old version can remain available for a quick rollback.

Why use it?

The new version can be validated before it receives production traffic.

Big advantage

Rollback can be as simple as switching traffic back to blue.

Trade-off

You temporarily need capacity for both environments.

Strategy 04 Deployment pattern

Canary deployment

Release the new version to a small portion of users or traffic first. If metrics look healthy, gradually increase its traffic share until the new version becomes the default.

Observe

Watch error rate, latency, saturation, business metrics, and logs.

Increase

Gradually expose more traffic when the new version behaves well.

Abort

Stop or reverse the rollout when the metrics indicate a problem.

Important Kubernetes nuance

A plain Kubernetes Service does not automatically give you precise percentage-based traffic splitting. Canary releases are commonly implemented with Ingress/Gateway traffic rules or tools such as Argo Rollouts and service meshes.

Kubernetes detail

Recreate vs RollingUpdate in a Deployment

Recreate

spec:
  strategy:
    type: Recreate

RollingUpdate

spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

Key distinction

Blue-green and canary are best thought of as deployment patterns built from Kubernetes primitives, not simply extra values for spec.strategy.type. You can implement them using multiple Deployments, Services, labels/selectors, Ingress or Gateway routing, and specialized rollout tooling.

A simple decision guide

→

“I don't care about downtime.”

Use Recreate.

→

“I want a normal, highly available rollout.”

Use RollingUpdate.

→

“I want the new environment completely ready before switching.”

Consider Blue-green.

→

“I want to expose only a small percentage first.”

Consider Canary.

Bottom line

Recreate and RollingUpdate are Kubernetes Deployment strategies. Blue-green and canary are broader release patterns that you can implement on top of Kubernetes. So if someone says there are only two deployment strategies in Kubernetes, they are usually talking specifically about the two values supported by the Deployment's strategy.type.
