ACID vs BASE

Posts

Distributed data systems

Every database has to answer one question: when things go wrong -- a crash, a network hiccup, two people editing the same row at once -- what does the data look like afterward? ACID and BASE are two different sets of answers. ACID promises the data is always correct, even if that means saying "no" sometimes. BASE promises the system keeps responding, even if that means the data is briefly wrong.

One concrete thing to anchor on before the acronyms: PostgreSQL is an ACID database by default. Every plain transaction you write in Postgres already gets ACID guarantees for free. BASE isn't a competing database feature you turn on instead -- it's a set of trade-offs you deliberately introduce on top (async replication, caches, precomputed counters) when you decide strict correctness isn't worth the cost for a particular piece of data.

Correctness first

ACID

A transaction model designed to preserve correctness and predictable behavior, especially when multiple operations must succeed or fail together.

Atomicity
All operations commit, or none do.
Consistency
A committed transaction preserves defined database invariants.
Isolation
Concurrent transactions behave according to the chosen isolation level.
Durability
Committed data survives failures, subject to the database's guarantees.

Typical fit

Bank transfers, orders, inventory, accounting, reservations, and other workflows where incorrect state is costly.

Availability & scale

BASE

A family of approaches that favors remaining responsive and scalable in distributed environments, often allowing replicas to converge over time.

Basically Available
The system aims to keep responding even during some failures.
Soft state
State may change over time as replicas synchronize.
Eventually consistent
If updates stop and the system can communicate, replicas are expected to converge eventually.

Typical fit

Feeds, likes, counters, product catalogs, caches, globally distributed content, and workloads that can tolerate short-lived stale reads.

Letter by letter

ACID in PostgreSQL

Every one of these is something Postgres gives you automatically once you wrap statements in a transaction. Here is what each letter actually does, with the SQL that demonstrates it.

A -- Atomicity

A transaction is one unit: either every statement in it takes effect, or none of them do. Money can never leave one account without arriving in the other, even if the server crashes mid-transaction. 

BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT;
-- If either UPDATE fails, or you run ROLLBACK instead of COMMIT,
-- neither balance changes. There is no "half transfer" state.
flowchart LR
    A["BEGIN"] --> B["UPDATE accounts: balance -= 100 WHERE id=1"]
    B --> C["UPDATE accounts: balance += 100 WHERE id=2"]
    C --> D{"Both succeeded?"}
    D -->|Yes| E["COMMIT: both balances updated"]
    D -->|No| F["ROLLBACK: neither balance changed"]

C -- Consistency

A committed transaction can never leave the database violating its own rules -- constraints, foreign keys, and checks you defined. Postgres enforces this for you; it simply refuses to commit a transaction that would break an invariant. 

CREATE TABLE accounts (
  id      serial PRIMARY KEY,
  balance numeric NOT NULL CHECK (balance >= 0)
);

INSERT INTO accounts (id, balance) VALUES (1, -50);
-- ERROR: new row for relation "accounts" violates
--        check constraint "accounts_balance_check"
-- The invariant "balance can never go negative" always holds.

I -- Isolation

Concurrent transactions shouldn't see each other's half-finished work. Postgres defaults to READ COMMITTED, but you can ask for stronger guarantees like SERIALIZABLE when two transactions must not be allowed to conflict silently. 

-- Transaction A
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT balance FROM accounts WHERE id = 1; -- reads 100
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
COMMIT;

-- Transaction B, running concurrently, also reads balance = 100
-- and tries to subtract 30. Postgres detects the conflict:
-- ERROR: could not serialize access due to concurrent update
-- Transaction B must retry instead of silently overwriting A's work.
sequenceDiagram
    participant A as Transaction A
    participant DB as PostgreSQL
    participant B as Transaction B
    A->>DB: BEGIN (SERIALIZABLE)
    B->>DB: BEGIN (SERIALIZABLE)
    A->>DB: SELECT balance WHERE id=1 -> 100
    B->>DB: SELECT balance WHERE id=1 -> 100
    A->>DB: UPDATE balance = 100 - 50
    A->>DB: COMMIT (succeeds)
    B->>DB: UPDATE balance = 100 - 30
    B->>DB: COMMIT
    DB-->>B: ERROR: could not serialize access
    Note over B,DB: B must retry with the now-current balance

D -- Durability

Once Postgres tells the client "COMMIT" succeeded, that data survives a crash or power loss. It does this by writing every change to the Write-Ahead Log (WAL) on disk before acknowledging the commit. 

SHOW fsync;               -- on: changes are flushed to disk, not just OS cache
SHOW synchronous_commit;  -- on: COMMIT waits until the WAL write is flushed

-- If the server crashes right after COMMIT returns, on restart Postgres
-- replays the WAL and the committed row is still there.
flowchart LR
    A["Client: COMMIT"] --> B["Write change to WAL on disk"]
    B --> C["Acknowledge commit to client"]
    C --> D["Crash / power loss"]
    D --> E["Restart: recovery replays WAL"]
    E --> F["Committed data is intact"]

CAP theorem: the constraint behind the trade-off

CAP says that a distributed system cannot simultaneously guarantee all three of these properties when a network partition occurs. You must choose how the system behaves during that partition.

C

Consistency

Every read sees the latest successful write (linearizable behavior).

A

Availability

Every request receives a non-error response, though it may not contain the newest data.

P

Partition tolerance

The system continues operating despite messages being delayed or lost between nodes. 

flowchart TD
    P["Network partition occurs (a replica can't reach the primary)"] --> C{"What does the system do?"}
    C -->|"Favor Consistency"| Reject["Reject/block requests on the cut-off side until it heals"]
    C -->|"Favor Availability"| Serve["Keep serving reads and writes, some of it may be stale"]

Important correction

CAP is not simply "ACID vs BASE," and it does not say a database must choose two letters all the time. Partition tolerance is generally required in a distributed system; the key CAP decision is what the system sacrifices during a partition: consistency or availability. A system can also offer ACID transactions while being distributed, and BASE is not a single standardized protocol.

Getting BASE behavior

BASE isn't a Postgres mode -- it's architecture on top

A single Postgres primary is ACID. You get BASE-style trade-offs when you deliberately add pieces that relax strict consistency in exchange for availability or scale: asynchronous replicas, precomputed counters, materialized views refreshed on a schedule. Below are the two most common ways teams do this with Postgres.

1. Asynchronous replication ("basically available")

A primary accepts writes and immediately acknowledges them without waiting for a replica to catch up. Reads sent to the replica (common for scaling out read traffic) can briefly return stale data. This is the "soft state" / "eventually consistent" part of BASE in practice. 

-- On the primary: don't wait for the replica to confirm before
-- acknowledging the write to the client
ALTER SYSTEM SET synchronous_commit = 'local';

-- postgresql.conf on the replica:
-- primary_conninfo = 'host=primary-db port=5432 user=replicator ...'
-- hot_standby = on

-- The app writes to the primary...
INSERT INTO post_likes (post_id, user_id) VALUES (42, 7);
-- ...and COMMIT returns right away. The replica applies this
-- WAL record a moment later, asynchronously.
sequenceDiagram
    participant App as Application
    participant Primary as Primary (writes)
    participant Replica as Read replica (async)
    App->>Primary: INSERT INTO post_likes ...
    Primary-->>App: COMMIT acknowledged (durable on primary)
    Primary--)Replica: WAL streamed asynchronously
    App->>Replica: SELECT count(*) FROM post_likes WHERE post_id=42
    Replica-->>App: Returns count from a moment ago (stale)
    Note over Replica: A few ms/sec later, replica catches up

This is exactly why "read your own write" bugs happen: a user likes a post, the app reads it back from a lagging replica, and the like briefly appears missing. Whether that's acceptable is a product decision, not a database one.

2. Precomputed / periodically refreshed views ("eventually consistent")

Instead of computing an expensive aggregate (like counts, feeds, dashboards) on every read, compute it once and refresh it on a schedule. Readers get a fast answer that is correct as of the last refresh, not as of right now. 

CREATE MATERIALIZED VIEW like_counts AS
SELECT post_id, count(*) AS likes
FROM post_likes
GROUP BY post_id;

CREATE UNIQUE INDEX ON like_counts (post_id);

-- Run every 30s via pg_cron, a worker, or a scheduled job --
-- not on every single like:
REFRESH MATERIALIZED VIEW CONCURRENTLY like_counts;

-- Reads are cheap and fast, but "likes" can lag reality by up to 30s.
SELECT likes FROM like_counts WHERE post_id = 42;

Concrete examples

Same company, different data can use different guarantees

E-commerce checkout -- use ACID

Payment, order creation, and inventory reservation need strong transactional guarantees. Overselling a scarce item is worse than briefly rejecting checkout. 

BEGIN;
UPDATE inventory SET stock = stock - 1
  WHERE product_id = 9 AND stock > 0;
-- 0 rows updated means "out of stock": abort instead of overselling
INSERT INTO orders (product_id, user_id) VALUES (9, 7);
COMMIT;

Social-media likes -- use BASE

A user can usually tolerate seeing "1,239 likes" for a moment while another replica says "1,240." Availability and global scale matter more than an immediately identical count. 

-- Write hits the primary and returns immediately
INSERT INTO post_likes (post_id, user_id) VALUES (42, 7);
-- Read hits a replica/materialized view, may lag a bit
SELECT likes FROM like_counts WHERE post_id = 42;

Product catalog -- mix both

A price or compliance field needs stronger guarantees (ACID, on the primary) than a "customers also viewed" counter (BASE, precomputed). Real systems frequently mix consistency strategies per field.

Decision guide

Ask these questions first

  1. 1

    Can stale data cause harm?

    If yes, prefer stronger consistency for that operation.

  2. 2

    Must the service keep answering during partitions?

    If yes, you may need to accept stale or conflicting state and reconcile later.

  3. 3

    What does "consistent" actually mean?

    Distinguish transaction consistency, read-after-write guarantees, causal consistency, and linearizability. They are not interchangeable.

  4. 4

    What happens after a conflict?

    For eventually consistent systems, define conflict resolution, idempotency, retries, and reconciliation -- not just "it will eventually sync."

One more useful concept

CAP is about partitions; PACELC explains the normal case too

PACELC extends the discussion: if there is a Partition (P), choose Availability (A) or Consistency (C); Else (E), when the system is healthy, choose Latency (L) or Consistency (C). This helps explain why two distributed databases can both tolerate partitions yet make different latency/consistency trade-offs during normal operation.

A Postgres primary with a synchronous replica lives on the "choose Consistency" side even when healthy: every commit waits on the replica, adding latency. Switch synchronous_commit to local or off, and you've moved to the "choose Latency" side, trading a little consistency for speed even when nothing is broken.
