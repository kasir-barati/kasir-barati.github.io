Harness engineering · practical note

If you are practicing harness engineering you probably have PROCESS.md, REQUIREMENTS.md, SELF_IMPROVE.md, and maybe even a SELF_IMPROVE_LOG.md for details logs about what it improved each time, BUT what should be tracked by git and what happens when the feature is shipped?

⚙️

PROCESS.md

Reusable loop. Keep it and let improvements compound.

🧭

SELF_IMPROVE.md

Reusable self-critique ritual. Keep the mechanism.

📋

REQUIREMENTS.md

Feature-specific work. Archive it in the GitHub issue/PR, then remove it.

🧪

SELF_IMPROVE_LOG.md

Mine it for durable lessons, then archive it in GitHub issue/PR.

The useful distinction is between scaffolding and feature state. The files may look similar from feature to feature, but they do not all have the same lifecycle.

PROCESS.md and SELF_IMPROVE.md are usually the scaffolding. Once we have accumulated practical lessons, that knowledge is valuable institutional memory. Resetting them for every feature throws away exactly what harness engineering is meant to compound.
But not every rule learned deserves to be added to your AGENTS.md or CONTRIBUTING.md. That's were you can think about skills, but keep in mind skills have their own overhead; a separate file, a description that has to be specific enough to trigger correctly but not so narrow it never fires, and one more thing to keep in sync with the code. Skill description is the "index" now, helping LLMs to know when they should use them.

REQUIREMENTS.md is different: its job is to describe the current feature. When that feature ships, its requirements can live in the issue, PR, release notes, or simply git history. There is little reason to keep stale requirements at the repo root.

SELF_IMPROVE_LOG.md contains temporary entries, but then its discoveries are promoted as durable lessons into the docs (it can be a new skill, a new section or bullet point in AGENTS.md/CONTRIBUTING.md/any other permanent docs), once the log has been mined, archive it with the feature and let it go.

A simple lifecycle

Feature starts
Work + self-improvement
Promote durable lessons
Archive feature content

So you should not delete all four files and recreate them from a templates or something like that. That creates unnecessary churn and makes the process forgetful. Instead, keep the mechanism, discard the content that has completed its lifecycle.

Rule of thumb

Keep

Reusable mechanisms and accumulated process knowledge.

Archive

Feature requirements and raw improvement logs.

Promote

General lessons discovered during implementation.
