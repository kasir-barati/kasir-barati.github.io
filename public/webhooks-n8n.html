📘 Deep Dive: How the Routing Table Actually Works

🧠 Horizontal Scaling

  • Pod/Instance A accepts the request, stores res locally, and enqueues the job with its own instanceId.
  • Worker processes the job and publishes the result to a Redis channel named response:instance-A.
  • Only Pod/Instance A subscribes to that channel. It receives the result, looks up res, and sends the HTTP response.

This allows true round-robin load balancing (stateless LB), automatic failover for new requests, and zero shared memory between pods/instances.

💡 Pro Tips for Implementation

  • Timeout: Always implement setTimeout to delete pending entries and send a 408 status.
  • Logging: Log every dynamic route change for debugging.
  • Graceful Shutdown: On server shutdown, iterate pending map and send 503 to hanging requests.
