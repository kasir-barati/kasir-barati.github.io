Every NestJS tutorial ends at the same place: a controller calls a service, the service calls an ORM. It works. Then the app grows, the rules multiply, and nobody can change anything without breaking something else. This post walks through the three ideas that helps you to build a maintainable, testable, and reliable solution following domain-driven design, CQRS and modular architecture.

1. Where the Default MVC Breaks

The standard flow is familiar: controllers handle HTTP and delegate to services, services hold most of the business logic, services use repositories to persist entities, and entities are containers of values with getters and setters. The NestJS docs describe exactly this shape and note it is usually fine for small and medium applications.

The trouble starts when the rules get real. Say the shop needs to answer: what makes an order successful, how is a total calculated, when does a discount apply, can this order still be cancelled? Those answers have to live somewhere, and in the default shape they end up spread across services. OrderService asks UserService whether a customer is active, UserService asks PaymentService for a refund, and PaymentService reaches back into OrderService to update a status. Three symptoms follow.

Data and behaviour drift apart

The entity holds the fields; some service somewhere holds the rule about those fields. Nothing stops a second service from writing its own version of the same rule, so there are two sources of truth and no way to tell which one ran.

Every service touches the database

Once services call each other and all of them call the ORM, you get circular dependencies and no isolated place to reason about a rule. Testing one rule means standing up a database.

The framework becomes the foundation

Rules end up inside controllers, ORM models and decorators. Swapping a database, a payment SDK or a transport means touching business logic that had nothing to do with the change.

Notice that all three are the same problem wearing different clothes: the parts of the system that change most often are frameworks, databases, SDKs, transports. They are entangled with the parts that should change least, the business rules. Everything below is about separating those two by volatility.

2. Three Layers and One Rule

A clan and modular architecture arranges the application as concentric layers, with the business at the centre and the technology at the edge.

Domain

The rules of the business, modelled as plain TypeScript. "What an order total means? When a SKU is valid? Whether stock can go negative?", a product person could describe these without knowing what a database is.

What is not here matters just as much: no HTTP, no SQL, no ORM models, no NestJS decorators, no SDKs. The domain doesn't know where data comes from or when it gets saved.

Application

Use cases are about what the user is trying to accomplish. "Create a product, place an order, pay for it.", this layer orchestrates: it loads or creates domain objects, calls methods on them, enforces authorization, manages transactions.

It still doesn't know which database is running or whether the transport is REST or GraphQL. It talks to interfaces only.

Infrastructure

Everything that touches the outside world: controllers, repositories, external APIs, email providers, ORM choices, exception filters.

This is the most volatile layer, which is exactly why it sits on the outside where change is cheap.

The Dependency Rule

Dependencies always point inward. Infrastructure may depend on application; application may depend on domain; the domain depends on nothing. Swap the database and only the infrastructure layer is affected, because nothing inward of it holds a reference to it. Move from REST to GraphQL, or from a monolith to microservices, and the domain and application layers compile unchanged.

This is the mindset shift: frameworks become implementation details rather than the foundation. Software evolves around the business instead of around the tools you happen to be using this year.

3. Modelling the Domain

Domain-driven design supplies the vocabulary for that innermost layer. Three building blocks carry most of the weight.

Entities Keep Data and Behaviour Together

An entity has an identity that persists through change. In practice it is a plain class holding both the domain data (order id, product name, SKU) and the methods that act on that data. That co-location is the whole point. When the rule lives next to the field it governs, there is exactly one place to change it, and no service can quietly implement a rival version.

src/shared/domain/entity.ts 
import { UniqueId } from './value-objects/unique-id.vo';

export abstract class Entity<T extends UniqueId = UniqueId> {
  constructor(protected readonly id: T) {}

  getId(): T {
    return this.id;
  }

  equals(other: Entity<T>): boolean {
    if (other === null || other === undefined) return false;
    if (this === other) return true;
    return this.id.equals(other.id);   // entities compare by identity
  }
}

Value Objects are Immutable and Self-validating

A value object has no identity; it is its value. Two SKUs with the same string are the same SKU. They earn their place for three reasons: they keep the entity from bloating with loosely related fields and helpers, they validate themselves so an invalid instance cannot exist, and being immutable they remove a whole category of runtime bug where some far-off line reassigns money.amount to something nobody expected. AKA you would be having an object value for money to make sure you won't be running into logical runtime bugs.

The question of when to extract one has no clean answer. The useful heuristic: peel off groups of related properties and the functions over them, especially properties that should never change once set.

src/shared/domain/value-objects/unique-id.vo.ts 
import { randomUUID } from 'crypto';

export class UniqueId {
  private readonly value: string;   // private: data stays hidden

  constructor(id?: string) {
    this.value = id ?? randomUUID();
  }

  getValue(): string {
    return this.value;
  }

  equals(other: UniqueId): boolean {
    return this.value === other.value;
  }

  toString(): string {
    return this.value;
  }
}
src/product/domain/value-objects/sku.vo.ts 
export class Sku {
  private static readonly SKU_PATTERN = /^[A-Za-z0-9-]+$/;
  private static readonly MIN_LENGTH = 3;
  private static readonly MAX_LENGTH = 50;

  private readonly value: string;

  private constructor(value: string) {   // only create() can build one
    this.value = value;
  }

  static create(value: string): Sku {
    const trimmed = value.trim();

    if (trimmed.length < Sku.MIN_LENGTH ||
        trimmed.length > Sku.MAX_LENGTH) {
      throw new DomainException(
        `SKU must be between ${Sku.MIN_LENGTH} and ${Sku.MAX_LENGTH} characters`,
      );
    }
    if (!Sku.SKU_PATTERN.test(trimmed)) {
      throw new DomainException(
        `SKU must contain only alphanumeric characters and dashes`,
      );
    }
    return new Sku(trimmed.toUpperCase());
  }

  equals(other: Sku): boolean {   // value objects compare by value
    return this.value === other.value;
  }

  getValue(): string {
    return this.value;
  }
}

A private constructor plus a static factory means there is no path to an invalid Sku anywhere in the system. The messy validation is hidden behind one call, and every consumer gets it for free.

Aggregate Roots are the Consistency Boundary

An aggregate is a cluster of related domain objects treated as one unit, and the aggregate root is its single entry point. Outside code never reaches inside to fiddle with a part; it calls a method on the root, and the root enforces the invariants for everything it contains. This is what guarantees that a rule cannot be bypassed. No second door.

In NestJS the AggregateRoot class from @nestjs/cqrs also gives the model event-publishing ability, which section 8 uses. Wrapping it in your own abstraction keeps the coupling in one file:

src/shared/domain/aggregate-root.ts 
import { AggregateRoot as CqrsAggregateRoot } from '@nestjs/cqrs';

export abstract class AggregateRoot extends CqrsAggregateRoot {}

Worth being honest about the trade: this is a thin alias, but the NestJS import is still in the domain layer. If you want the domain genuinely framework-free, @nestjs/cqrs exposes an IAggregateRoot interface you can implement yourself, EventPublisher accepts anything that satisfies it. There is also a WithAggregateRoot() mixin for when you already have a base Entity class and can't spend your one inheritance slot on the framework.

Put together, an entity looks like this: private fields, getters, a static factory that validates, and a separate reconstitute used by repositories to rebuild an instance from storage without re-running creation rules:

src/product/domain/entities/product.entity.ts -- abridged 
export class Product extends AggregateRoot {
  private _sku: Sku;
  private _price: Money;
  private _stock: number;
  // ...

  private constructor(props: ProductProps) { /* ... */ }

  static create(
    name: string, description: string, sku: string,
    price: number, currency: string, stock: number,
  ) {
    Product.validateName(name);
    Product.validateStock(stock);

    return new Product({
      id: new ProductId(),
      name,
      description,
      sku: Sku.create(sku),
      price: Money.create(price, currency),
      stock,
      isActive: true,
      lowStockThreshold: 5,
      createdAt: new Date(),
      updatedAt: new Date(),
    });
  }

  static reconstitute(props: ProductProps): Product {
    return new Product(props);   // rebuild from persistence
  }

  private static validateStock(stock: number): void {
    if (stock < 0) {
      throw new DomainException('Stock cannot be negative');
    }
  }
}

No Mongoose, no Prisma, no decorators. That is what makes the persistence layer swappable rather than load-bearing.

4. Ports and Adapters

A fair objection to the dependency rule: the application layer has to save things and charge cards. It genuinely needs infrastructure. How can it use the outer layer without depending on it?

Ports and adapters. A port is an interface, owned by the application layer. An adapter is an implementation of it, living in infrastructure. The application programs against the interface and never learns which implementation showed up (Stripe or PayPal, Mongo or Postgres). The arrow of dependency points from the adapter to the port, which is inward, so the rule holds.

export const PRODUCT_REPOSITORY = Symbol('PRODUCT_REPOSITORY');

export interface ProductRepository {
  save(product: Product): Promise<void>;
  findById(id: ProductId): Promise<Product | null>;
  findBySku(sku: Sku): Promise<Product | null>;
  findByName(name: string): Promise<Product | null>;
  findAll(filters: ProductFilters): Promise<Product[]>;
  delete(id: ProductId): Promise<void>;
}
src/product/infrastructure/repositories/mongo-product.repository.ts -- abridged 
export class MongoProductRepository implements ProductRepository {
  private readonly collection: Collection<ProductDocument>;

  constructor(@Inject(MONGO_DB) private readonly db: Db) {
    this.collection = this.db.collection<ProductDocument>('products');
  }

  async save(product: Product): Promise<void> {
    const doc = MongoProductRepository.toPersistence(product);
    await this.collection.updateOne(
      { _id: doc._id }, { $set: doc }, { upsert: true },
    );
  }

  // the two mappers are where the coupling is contained
  private static toDomain(doc: ProductDocument): Product {
    return Product.reconstitute({
      id: new ProductId(doc._id),
      sku: Sku.create(doc.sku),
      price: Money.create(doc.priceAmount / 100, doc.priceCurrency),
      // ...
    });
  }

  private static toPersistence(product: Product): ProductDocument {
    return {
      _id: product.id.getValue(),
      sku: product.sku.getValue(),
      priceAmount: product.price.toCents(),
      priceCurrency: product.price.getCurrency(),
      // ...
    };
  }
}

Notice the two static mappers. All the translation between domain shapes and storage shapes is confined there, money as cents, value objects as strings & so the domain never learns that Mongo prefers a flat document with a _id.

NestJS providers are what make the swap trivial: bind the PRODUCT_REPOSITORY token to whichever adapter you want, choose it from an environment variable at bootstrap, and the entire application and domain layers stay untouched. That is the payoff for all the ceremony above & one variable changes the database and nothing else moves.

5. CQRS, and What it Actually is

One question is still open. The controller has to reach a use case somehow. Injecting a service puts a compile-time reference to a concrete class in the presentation layer. The most volatile part of the system now knows the name of something inward of it. CQRS is the usual answer, but the term covers three different ideas at three different levels, and most confusion comes from mixing them up.

CQS -- the Principle

Bertrand Meyer's rule that a method either changes state or returns state, never both. Asking a question shouldn't change the answer. It applies inside a single object and costs nothing.

CQRS & the Pattern

Greg Young's extension of that from methods to models: use one model to change information and a different one to read it. Everything expensive about CQRS follows from maintaining two models.

@nestjs/cqrs -- the library

An in-process message bus: CommandBus, QueryBus, EventBus, handler decorators, aggregate roots and sagas. It enables the pattern; it does not impose it.

Warning
If a controller dispatches CreateProductCommand, a handler catches it and calls productService.create(), you have installed the library and gained an expensive router. You get the pattern only when the read side stops going through the domain model. Until then the honest comparison is "bus versus injected service", and the bus wins by a much smaller margin than what you think unless you really need it.

Commands Carry Intent

The first real payoff. Commands should be task-based rather than data-centric. The NestJS pattern catalogue put it that way. Compare what a single CRUD endpoint has to do against what three commands do:

Intent has to be GUESSED from the payload 
// PATCH /products/:id
class UpdateProductDto {
  price?: number;
  stock?: number;
  isActive?: boolean;
  skipAudit?: boolean;      // flags start appearing
  notifyCustomers?: boolean;
}

// and inside the service:
//   is this a reprice? a restock? a deactivation?
//   should stock changes emit a low-stock warning?
//   three business processes, one method body
Intent ARRIVES with the message 
class RepriceProductCommand { /* id, price, currency */ }
class RestockProductCommand { /* id, quantity */ }
class DeactivateProductCommand { /* id, reason */ }

// each handler is one use case with one reason to exist,
// and each rule has exactly one home on the aggregate:
//   product.reprice(...)
//   product.restock(...)
//   product.deactivate(...)

Audit trails come along free: a stream of ProductRepriced tells you what the business did, while a stream of UPDATE products SET ... tells you what the database did. Worth noting though: naming intent is a modelling discipline, not a bus feature. You could write reprice() and restock() as separate service methods today. What CQRS adds is that the discipline becomes structural: one command, one handler, one file.

It survives the deadline where a service method would have grown a boolean parameter.

What it Looks Like in Code

The controller translates HTTP into a message and nothing else. It holds no reference to any handler:

src/product/presentation/product.controller.ts -- abridged 
@Controller('products')
export class ProductsController {
  constructor(
    private readonly commandBus: CommandBus,
    private readonly queryBus: QueryBus,
  ) {}

  @Post()
  async create(@Body() dto: CreateProductDto): Promise<void> {
    await this.commandBus.execute<CreateProductCommand, void>(
      new CreateProductCommand(
        dto.name, dto.description, dto.sku,
        dto.price, dto.currency || 'USD', dto.stock,
      ),
    );
  }

  @Get(':id')
  async findOne(
    @Param('id', new ParseUUIDPipe()) id: string,
  ): Promise<ProductResponseDto> {
    const product = await this.queryBus.execute<GetProductQuery, Product>(
      new GetProductQuery(id),
    );
    return ProductResponseDto.fromDomain(product);
  }
}

The command itself is a plain data class with no framework in it, which is why any transport (a queue consumer, a CLI script, a cron job) can dispatch the same one:

application/use-cases/create-product/create-product.command.ts 
export class CreateProductCommand {
  constructor(
    public readonly name: string,
    public readonly description: string,
    public readonly sku: string,
    public readonly price: number,
    public readonly currency: string,
    public readonly stock: number,
  ) {}
}
application/use-cases/create-product/create-product.handler.ts 
@CommandHandler(CreateProductCommand)
export class CreateProductHandler
  implements ICommandHandler<CreateProductCommand, void> {
  constructor(
    @Inject(PRODUCT_REPOSITORY)          // a port, not an adapter
    private readonly productRepository: ProductRepository,
  ) {}

  async execute(command: CreateProductCommand): Promise<void> {
    const existing = await this.productRepository.findBySku(
      Sku.create(command.sku),
    );
    if (existing) {
      throw new ApplicationException(    // no HTTP status here
        `Product with SKU ${command.sku} already exists`,
        ApplicationExceptionCode.CONFLICT,
      );
    }

    const product = Product.create(/* ... */);
    await this.productRepository.save(product);
  }
}

Two details there carry the architectural weight. The repository arrives through an injection token bound to an interface, so the database is a provider swap. And the error is an application-level code rather than ConflictException, which is what stops the application layer from importing the presentation layer. Section 7 finishes that thought.

Queries mirror all of this; a GetProductQuery data class and a @QueryHandler implementing IQueryHandler. Handlers must be registered as providers in their module, or the bus has nothing to route to.

Three smaller things worth knowing about the library. The optional Command and Query base classes exist only to declare a return type, so execute() infers it. All three buses are RxJS observables, so you can subscribe to the whole stream for logging, tracing or persisting events. And the default publishers are in-memory, out of the box this is an in-process mediator, not a distributed broker, so commands are not durable and a crash mid-handler loses what was in flight.

6. Separate Read and Write Models

Here is the part that makes CQRS more than routing. In the default shape one ProductEntity serves three masters: persistence wants normalized tables, validation wants a DTO, the frontend wants a shaped response. It does none of them especially well. A dashboard ends up joining six tables through the domain model, and that cost lands on the same code path that enforces your invariants.

Split it. The write side keeps rich aggregates with strict invariants. The read side keeps flat models shaped like the screens that consume them. No aggregate loading, no value object reconstruction, sometimes just raw SQL into a DTO.

The asymmetry is the point: the query handler never touches the aggregate. Microsoft's catalogue frames the benefits as cleaner separation of responsibilities, simpler queries once you store a materialized view, and the freedom to scale or even store the two sides independently. You can have a document store for reads, a relational one for writes.

In CQRS when it comes to how deep you can go we have 3 levels: from just using a fancy router, all the way to splitting your database in two. Think of it as a sliding scale of investment: the further down you go, the more performance and structural benefits you get, but the more complexity and operational headaches you take on.

Level What Changes What it costs
Buses only You download the CQRS library and split your code into Commands (write) and Queries (read). However, underneath the hood, both paths still load the exact same Product class from the exact same SQL table. The only thing separating them is the code path (the route the code takes). Boilerplate, and nothing else.
Two models, one store You keep your main, normalized database for writes (saving data). But for reading data (like displaying a list of products), you completely bypass your complex domain model. Instead, you write fast, raw SQL queries that grab exactly the columns you need for that specific screen and map them straight into a plain, flat DTO. Two separate translators: one to turn database rows into your complex Domain objects (for writes), and another to turn database rows into your simple DTOs (for reads).
Two models, two stores Create a completely separate read-only database (like a separate table structure, or even a totally different technology like Elasticsearch or Redis). Whenever data is saved on the "write" side, it fires an event. A background process (the Projection handler) listens to this event and updates this new read-database in the background. · Eventual consistency.
· If this read-database gets corrupted or has a bug, you need complex tools to replay all past events to rebuild it from scratch.
· Clients should be able to tolerates lags.

Level two is where most teams should stop. It buys the read performance and the clean write model without asking your product manager to explain to users why the order they just placed isn't on the list yet. Level three is a genuine architecture change, not a refactor.

7. Errors Across the Boundary

Error handling is where a clean, modular architecture quietly leaks in most codebases. Throwing ConflictException from a handler drags an HTTP concept into the application layer, and now the least volatile code knows about the most volatile transport. Instead we should have two exception types and two filters:

src/shared/domain/exceptions/application.exception.ts 
export enum ApplicationExceptionCode {
  VALIDATION_ERROR = 'VALIDATION_ERROR',
  NOT_FOUND = 'NOT_FOUND',
  CONFLICT = 'CONFLICT',
}

export class ApplicationException extends Error {
  constructor(
    message: string,
    public readonly code: ApplicationExceptionCode =
      ApplicationExceptionCode.VALIDATION_ERROR,
  ) {
    super(message);
    this.name = 'ApplicationException';
  }
}
src/shared/infrastructure/filters/application-exception.filter.ts 
const CODE_TO_HTTP: Record<ApplicationExceptionCode, HttpStatus> = {
  [ApplicationExceptionCode.VALIDATION_ERROR]: HttpStatus.BAD_REQUEST,
  [ApplicationExceptionCode.NOT_FOUND]: HttpStatus.NOT_FOUND,
  [ApplicationExceptionCode.CONFLICT]: HttpStatus.CONFLICT,
};

@Catch(ApplicationException)
export class ApplicationExceptionFilter implements ExceptionFilter {
  catch(exception: ApplicationException, host: ArgumentsHost) {
    const response = host.switchToHttp().getResponse<Response>();
    const status =
      CODE_TO_HTTP[exception.code] ?? HttpStatus.INTERNAL_SERVER_ERROR;

    response.status(status).json({
      statusCode: status,
      message: exception.message,
    });
  }
}

The enum is a transport-agnostic vocabulary; the filter is the one place that knows HTTP exists. Move to gRPC or a queue consumer and you write a different filter, not a different handler.

DomainException is the simpler sibling, no code, no status, just a message. Because the only errors a domain model should raise are about its own data being invalid. It carries no status code precisely because the domain layer must not know the presentation layer is HTTP. Duplicate-checking, authorization and other orchestration concerns belong to the application layer, which is why CreateProductHandler does the SKU-uniqueness check while Sku.create() only enforces what a valid SKU looks like.

8. Events and Side Effects

This is what most directly attacks the tangle from section 1. Without events, registering a customer means the handler calling a notification service, an analytics service and a CRM sync. Exactly the web of direct calls that produced circular dependencies. With events, the domain model announces what happened and whoever cares subscribes. 

sequenceDiagram
    autonumber
    participant C as Controller
    participant B as CommandBus
    participant H as Command handler
    participant A as Aggregate
    participant R as Repository port
    participant E as EventBus
    participant N as Notification handler

    C->>B: execute(RegisterCustomerCommand)
    B->>H: execute(command)
    H->>A: Customer.register(...)
    A-->>A: apply(CustomerRegisteredEvent)
    H->>R: save(customer)
    H->>A: commit()
    A->>E: publish event
    E-->>N: handle(event)
    N-->>N: send welcome message
    H-->>C: done

Mechanically: the aggregate records an event with apply(), but nothing is dispatched until the model is linked to the publisher. The command handler does that with EventPublisher.mergeObjectContext() and then calls commit(), or the model sets autoCommit = true and skips the explicit call. That deliberate gap between recorded and dispatched is what lets you save first and publish after, so a failed write never emits an event claiming otherwise.

The subscriber side is another port and adapter. The handler depends on a notification interface; then in production you can swap the console implementation for email or another means of sending notification without the handler noticing:

src/customers/application/ports/notification.port.ts 
export const NOTIFICATION_SERVICE = Symbol('NOTIFICATION_SERVICE');

export interface Notification {
  recipientId: string;
  subject: string;
  message: string;
}

export interface NotificationPort {
  sendNotification(notification: Notification): Promise<void>;
}
src/customers/application/events/customer-registered.handler.ts 
@EventsHandler(CustomerRegisteredEvent)
export class CustomerRegisteredHandler
  implements IEventHandler<CustomerRegisteredEvent> {
  constructor(
    @Inject(NOTIFICATION_SERVICE)
    private readonly notificationService: NotificationPort,
  ) {}

  async handle(event: CustomerRegisteredEvent) {
    await this.notificationService.sendNotification({
      recipientId: event.customerId,
      subject: 'Welcome',
      message: `Welcome to Clean Shop, ${event.firstName}!`,
    });
  }
}

A console adapter implementing that port may itself depend on the customer repository port to look up an email address. That direction is fine: a low-level implementation detail depending on a higher-level abstraction is exactly what the dependency rule asks for. The reverse is what you avoid.

Two sharp edges, straight from the docs

  • Exception filters do not cover event handlers. Errors thrown in a command handler still reach your filters. Errors in an event handler do not — you catch them yourself, or they land on the UnhandledExceptionBus stream, which nothing consumes until you subscribe to it. This is the most common way an event-driven NestJS app ends up silently inconsistent.
  • You cannot respond to the client from an event handler. The HTTP context is gone by then. If the client must learn the outcome, that means WebSockets, server-sent events, or polling.

For workflows spanning several aggregates (order placed, then payment authorized, then stock reserved) sagas listen to the event stream with RxJS operators and emit new commands, which the CommandBus dispatches asynchronously. That is where an orchestration service would otherwise grow into the god class everyone was trying to avoid.

Event sourcing, storing the events themselves as the source of truth rather than current state is the natural next step and is well supported here, since the buses are observable streams. It is a separate decision with its own weight, and CQRS does not require it.

9. What this Costs

Fowler, whose write-up popularized the term, is blunt: for most systems, “CQRS adds risky complexity”, and he urges real caution before adopting it. That is worth taking seriously rather than treating as an obligatory hedge at the end of this post 😉.

Indirection tax

Four files and a bus hop to answer "where does this run?". Stack traces get longer, jump-to-definition stops working across the dispatch, and a trivial feature pays the same overhead as a complex one.

Eventual consistency

Once projections are asynchronous, a user can create something and not see it on the next screen. That is a product and UI decision, not only a backend one.

Two models to keep honest

Every write-side field that reaches a screen needs a projection path. Projections drift, need rebuild tooling, and are their own category of bug.

Weaker transactional guarantees

Handlers dispatched from other handlers don't share a transaction by default. Multi-aggregate consistency becomes a saga with compensating actions rather than a BEGIN ... COMMIT.

Warning!
CQRS is not what stops business logic from smearing across forty services. Aggregates do that — putting the rule inside order.cancel() so there is one place to change it, and one door to reach it through. You can have that with plain services and no bus at all. CQRS makes the aggregate boundary harder to route around; it does not create it. So when we talk about CQRS and untangling a service layer, the working ingredient is the DDD.

10. Deciding, per Module

None of this is an all-or-nothing choice for a codebase. Bounded contexts differ, and it is normal for pricing and ordering to be full CQRS while the admin panel that manages product categories stays plain CRUD in the same repository.

A useful test before adding a command: can a domain expert who has never seen your code explain the rule that would reject it? If yes, that rule belongs on an aggregate and a command is the honest way to express the request. If the only rule is "this field is a non-empty string", you have a form rather than a domain, and a controller with a service is the right amount of machinery.

The short version

Keep the business rules in the middle, in plain TypeScript, expressed as entities and value objects that validate themselves and guard their own invariants. Point every dependency inward and reach outward only through interfaces, so databases and SDKs stay swappable. Then use CQRS where it earns its keep: requests that name a business intent, one handler per use case, side effects delivered as events instead of direct calls, and a read model that skips the domain entirely when reads and writes genuinely want different shapes.

Keep the CRUD modules boring, and you will have spent the complexity where it returns something.
