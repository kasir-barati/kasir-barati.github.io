AWS Flashcards

When does AWS auto-create a log group?

The general rule

AWS doesn't auto-create a CloudWatch log group for every service — only ones that produce execution/runtime logs as part of running your code (Lambda, CodeBuild, ECS with the awslogs driver, Step Functions, Glue, etc.) and have logs:CreateLogGroup, logs:CreateLogStream and logs:PutLogEvents permission in whatever role they execute under.

If the role can't create the log group, the service either fails to log (Lambda) or fails outright (some services validate at deploy time). So the presence of logs:Create* in an execution role's policy is the tell — that's the mechanism, not something arbitrary.

Naming isn't always "resource name" verbatim

It's a fixed prefix per service plus an identifier, and the identifier varies by service:

Service Log group pattern Identifier used
Lambda /aws/lambda/<function-name> function name
ECS (awslogs driver) the awslogs-group you set in the task def — not automatic; ECS won't create it unless you also set awslogs-create-group: true your choice
CodeBuild /aws/codebuild/<project-name> project name
API Gateway (execution logs) API-Gateway-Execution-Logs_<api-id>/<stage> API ID, not name
VPC Flow Logs user-specified when you create the flow log — not automatic your choice
RDS (exported DB logs) /aws/rds/instance/<db-instance-id>/<log-type> instance identifier
Step Functions /aws/vendedlogs/states/<state-machine-name>-Logs-<suffix> name + suffix
CloudTrail user-specified explicitly your choice
Amplify / AppSync / Glue, etc. varies, usually /aws/<service>/<resource> mixed

So: some services use the human-readable name (Lambda, CodeBuild), some use an opaque API ID you don't know until after creation (hard to pre-declare cleanly), and several don't auto-create at all — they require you to opt in explicitly (ECS, VPC Flow Logs, CloudTrail).

How to actually find out, per service, reliably

Don't try to memorize or guess — check two things when you add a new AWS resource:

  1. The resource's execution/service role policy — if it includes logs:CreateLogGroup, expect auto-creation. AWS-managed policies like AWSLambdaBasicExecutionRole are the giveaway — that policy literally grants logs:CreateLogGroup, logs:CreateLogStream, and logs:PutLogEvents on arn:aws:logs:*:*:*.
  2. The service's own docs page for "logging" — e.g. "Monitoring [X] with CloudWatch Logs" — it states explicitly whether it creates the group or requires you to pre-create it.

Rather than trying to predict names in advance, flip the dependency: for a Lambda function, strip logs:CreateLogGroup from its execution role and only grant logs:CreateLogStream/logs:PutLogEvents scoped to the log group Terraform already owns. If anything tries to auto-create a group you didn't declare, it fails loudly (permission denied) instead of silently leaking an unmanaged resource — a much more reliable way to catch this class of drift than enumerating every service's naming convention upfront.
